# 01 · 现状审计与问题清单（z-biz-tool-capability）

> 取证时点 2026-10-04，仓内 tag 至 `v0.2.0`。每条写清**量法**，便于自行复核。
> 凡没量到的写"没量到"，不写"没问题"。

## A. crates.io 名字占用（本次审计里最紧急的一条）

### A1 ⚠️ P0：`cap-audio` / `cap-video` 名字仍可被任何人占掉

- **量法**（必须带 User-Agent，否则 crates.io 回 403 而不是 404）：

      for n in cap-img cap-audio cap-video; do
        code=$(curl -s -o /tmp/cr.json -w "%{http_code}" \
               -H "User-Agent: z-biz-tool-audit (local)" \
               "https://crates.io/api/v1/crates/$n" --max-time 25)
        echo "$n → $code"
      done

- **2026-10-04 实测结果**：

  | 名字 | HTTP | 读法 |
  | --- | --- | --- |
  | `cap-img` | **200** | 已发布，最新 **0.2.0**，描述与本仓一致 |
  | `cap-audio` | **404** | **仍可注册 —— 未被占** |
  | `cap-video` | **404** | **仍可注册 —— 未被占** |

- 为什么是 P0：`PUBLISH.md` 同时写着两条约束 ——
  「crates.io 一旦发布**不可覆盖、不可删除**」与「名字可用性已核验：三者均 404」。
  前一条讲版本，后一条其实也适用于**名字**：crates.io 的 crate 名先到先得、
  永久占用。现在 `cap-audio` 仍是 404，而它是极通用的名字。

- ⚠️ **别把 403 当 404**：不带 User-Agent 请求时三个名字**都**回 403，
  看起来"三个都还空着"。403 的正确读法是**没量到**，不是"可注册"。
  （本轮第一次查就踩了这个，正则化的 shell 判断「非 200 即 404 可注册」
  会把 403 一起误报成可注册 —— 判据本身是错的，不是数据错。）

### A2 ✅ `cap-img` 发布状态与本仓一致

- **量法**：`curl … https://crates.io/api/v1/crates/cap-img` 后读 `crate.max_version`
- 实测 `max_version = 0.2.0`，与 `crates/cap-img/Cargo.toml` 的 `version = "0.2.0"` 一致；
  线上描述"图片处理原语：信息/缩略图/缩放/旋转/翻转/裁剪/滤镜/编码/EXIF（路径进→路径出，无状态）"
  与本仓定位相符。

## B. 代码实体度

### B1 ⚠️ 三个 crate 里两个是 4 行空壳

- **量法**：

      for c in crates/*/; do
        echo "$c $(wc -l < $c/src/lib.rs) 行"
        grep -cE 'pub (fn|struct|enum)' "$c/src/lib.rs"
      done

- 实测：

  | crate | `src/lib.rs` 行数 | 公开 API 数 | 测试标记 | 文件头 |
  | --- | --- | --- | --- | --- |
  | `cap-img` | 581 | 有（`ImageInfo`/`ImageThumbnail` + 多个 `pub fn`） | 23 | 正常文档注释 |
  | `cap-audio` | **4** | **0** | 0 | `//! cap-audio — 音频处理原语（占位）。` |
  | `cap-video` | **4** | **0** | 0 | `//! cap-video — 视频处理原语（占位）。` |

- 判读：这不是 bug，README 已声明是占位。问题在于**它们各自声明了
  `version = "0.1.0"`**，对外看起来像一个可用版本（见 C1）。

### B2 ✅ `cap-img` 是唯一有实体与测试的部分

- 581 行、公开 API 齐备、23 个测试标记。抽样 API：
  `info` / `thumbnail` / `export` / `save_bytes`，类型 `ImageInfo` / `ImageThumbnail`。
- ⚠️ 23 条测试的**断言强度本轮没逐条读** —— 知道数量与 CI 绿，
  不知道它们钉住的是行为还是只跑通不报错。

## C. 版本与发布面

### C1 ⚠️ 占位 crate 以 0.1.0 参与 workspace 版本面

- **量法**：读 `crates/*/Cargo.toml` 的 `[package].version`
- 实测：`cap-img 0.2.0` / `cap-audio 0.1.0` / `cap-video 0.1.0`。
- 家族审计已因此报 info「本仓版本分散在各 crate」——**那条 info 本身是对的**，
  但它只陈述事实，不指出「0.1.0 对外暗示有东西可用」这层含义。
- 两个选项（`publish = false` 显式不发布 / 保留版本但在 description 标注占位）
  各自的代价写在 00 的 P1，**本轮未决**。

### C2 ✅ 本仓 tag 齐整

- **量法**：`git tag --list` → `v0.1.0`、`v0.1.1`、`v0.2.0`
- 家族审计对本仓无 high/med 级问题（版本分散那条是 info）。

### C3 ℹ️ workspace 统一了依赖版本（做对了）

- **量法**：读仓根 `Cargo.toml` 的 `[workspace.dependencies]`
- `image` / `base64` / `serde` 三项集中声明，注释写明意图：
  「全家族的 Rust 依赖版本在此统一（矩阵规划 03 §4.2）：reqwest 0.12×6 仓 vs 0.13×1 仓、
  tokio features 各写各的这类分裂不再重演」。
- 这是**有意识的防分裂设计**，值得保留。
