## 本仓是什么

矩阵的**能力层**。图片 / 音频 / 视频处理原语，**双击打不开的一层**：
没有窗口、不发 DMG、不进 release-org，只被 pix / aigen / file / note 等仓
以 Rust 依赖方式静态链接进各自的 app。

> 详见 `z-biz-tool-lead/doc/矩阵规划/03_能力层与项目容器.md`。

## P0 —— crates.io 名字敞着，随时可能被别人占掉

`PUBLISH.md` 自己写着：

> 名字可用性已核验：crates.io 上 `cap-img` / `cap-audio` / `cap-video` 均 404（可注册）。

**2026-10-04 实测复核：这句话现在只对了一半。**

- `cap-img` → HTTP **200**，已发布 0.2.0，描述与本仓一致 ✅
- `cap-audio` → HTTP **404**，**仍未被占**
- `cap-video` → HTTP **404**，**仍未被占**

而 `PUBLISH.md` 另一处也写明了这个约束：

> crates.io 一旦发布**不可覆盖、不可删除**（只能 yank 撤下但版本号永久占用）。

**同名同理：crates.io 的 crate 名是先到先得、永久占用的。** `cap-audio` /
`cap-video` 是极通用的名字，任何第三方都可以随时注册掉它；一旦被占，
本仓就**永远无法**以这两个名字发布音频 / 视频能力 —— 而 `cap-audio` 正是
README 里写明的下一步方向（"接口待 creator 侧音频能力集中后定"）。

**这属于「现在花几分钟能消掉、以后只能改名」的窗口期问题。**
认领动作需要 crates.io API token，属于**对外可见的不可逆操作**，
本轮**未执行**，等确认后再做。

## P1 —— 占位 crate 不该以 0.1.0 参与 workspace 版本面

- `cap-audio` / `cap-video` 声明 `version = "0.1.0"`，但没有任何公开 API。
- 家族审计的 `check_version_consistency` 已经因此把本仓报成
  **info「本仓版本分散在各 crate（cap-audio=0.1.0，cap-img=0.2.0，cap-video=0.1.0）」**
  —— 这条 info 是对的，但它掩盖了一个问题：**0.1.0 对外暗示"有东西可用"**。
- 建议二选一（**本轮未决**）：
  a) 置 `publish = false`，等有真实 API 再开 —— 语义最诚实，且不影响 `cargo test`；
  b) 保留版本但在 `Cargo.toml` 的 `description` 里写明"占位，无公开 API"，
     并在 README 与 crates.io 搜索结果里都能看出来。
- ⚠️ 取舍：改 `publish = false` 后，若将来忘了改回来就发不出去。
  **所以这条要连同「何时改回」一起记，否则是个静默陷阱。**
