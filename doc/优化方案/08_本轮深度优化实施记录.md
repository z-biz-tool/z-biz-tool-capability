## 8.2 P2 的答案：23 条断言的强度实测

### 8.2.1 量法

不是「读起来觉得够不够」，而是**先分类、再用变异证伪**：

1. 逐条把 23 个 `#[test]` 按断言目标分类（验错误 / 验尺寸 / 验像素 / 验魔数 / 只验存在）；
2. 对每条「只验存在或成功」的，构造**能骗过它的假实现**，看它到底钉不钉得住。

**量法一（静态分类）** —— 逐条数断言覆盖了什么。

⚠️ **口径必须写清**，否则同一个「弱」字能被数出 12 条或 4 条两个答案：

- **宽口径**（无像素断言、无魔数断言、不验错误分支）= **12 条**，
  但其中 8 条是**字节级原语**（data URL / base64 / 魔数嗅探 / 帧编码），
  它们验的是**返回值本身**（`assert_eq!(parsed.bytes, bytes)` 这类），
  本来就不需要像素断言 —— 把它们算成"弱"是分类器的错，不是测试的错；
- **严口径**（本节采用）= **验的是"调用成功 / 文件存在"这类** ⇒ **4 条**。

| 判据类型（严口径） | 条数 |
| --- | --- |
| **只验「调用成功」/「文件存在且非空」** | **4** |
| 验错误分支（必须拒绝） | 6 |
| 验尺寸 / 字段值 | 5 |
| 验魔数 / 字节 | 5 |
| 验像素值 | 1 |
| 验字节级原语的返回值（data URL / base64 / 帧编码） | 8 |
| （其中 `info_actually_reads_exif_from_a_jpeg` 同时验像素与返回值） | — |

那 4 条「只验存在」是：

| 测试 | 钉不住什么 |
| --- | --- |
| `resize_still_writes_and_creates_parent` | resize 实现成**原样拷贝**也过（只查文件存在 + 非空） |
| `transform_family_round_trips` | 5 个变换全部只 `unwrap()`，**零条 assert**；rotate/flip/filter 实现成恒等也全绿 |
| `info_still_reads_an_ordinary_file` | `size` 恒填 0、`has_alpha` 恒填 false 都过 |

## 8.3 查出的三个真缺陷

三条都是**先补断言、再打红**时暴露的，不是读代码读出来的。

### 8.3.1 `crop` 坐标溢出 —— debug panic / release 静默回绕

`src/lib.rs` 原判据：`if x + w > img.width() || y + h > img.height()`。

`x` 来自调用方（file 仓的 `crop_image` 命令直接透传前端参数），不是内部常量。
`x = u32::MAX` 时 `x + w`：

- **debug**：直接 panic（`attempt to add with overflow`）；
- **release**：回绕成 3 ⇒ `3 > width` 为假 ⇒ **越界检查被绕过**。

两个都是缺陷：debug 是崩溃，release 是静默放行。

**修法**：`checked_add`，溢出与超范围走同一条错误出口。
**实测**：现在返回 `Err 裁剪区域尺寸溢出: 裁剪(4294967295,0)+4x4`，不 panic。

### 8.3.2 EXIF 的 IFD0 越界 —— 切片 panic

`parse_exif_minimal` 原判据：`if ifd0_offset >= data.len()`，
随后 `read_u16(&data[ifd0_offset..ifd0_offset + 2])`。

检查只比**起点**，没比**要读的整个区间** ⇒ `offset == len - 1` 时切片越界 panic。
而这个 offset 是**图片文件里的字节**，任何人都能手搓一个 JPEG 触发。

**实测**（修复前）：往真 JPEG 里插一段 `offset=8、长度 9` 的 EXIF，
`info()` 直接 panic —— 不是返回 Err。调用方（file 仓 `get_image_info`）只当它是个坏文件。

**修法**：`if ifd0_offset + 2 > data.len()`。
**实测**（修复后）：返回 `Some(空表)`，不 panic。

### 8.3.3 「名字说谎」的文件 —— 变换族与 export 各写各的

同一个 crate 里两套规则：

- `save_bytes` **早就**拒绝「format 与扩展名不符」（注释写明：否则磁盘上出现
  一个"名字说谎"的文件，双击打不开还不知道为什么）；
- 但变换族（resize/rotate/flip/crop/filter）按**源图**扩展名决定输出格式，
  `export` 按**参数**决定 —— 两者都**不看目标扩展名**。

**实测**（修复前）：

| 调用 | 目标文件里实际是什么 |
| --- | --- |
| `resize("a.png", "out.jpg")` | **PNG** 字节（文件叫 .jpg） |
| `export("a.png", "out.png", "jpeg", 90)` | **JPEG** 字节（文件叫 .png） |

**修法**：

- 变换族：**目标扩展名**决定输出格式；目标无扩展名（调用方明确要无后缀文件）才回落源图格式；
  目标扩展名认不出来**报错**，不悄悄写 PNG；
- `export`：`format` 与目标扩展名必须一致，否则**拒绝**（与 `save_bytes` 同一规则）；
- 写 JPEG 时显式先降 RGB（JPEG 无 alpha 通道）。

**实测**（修复后）：`out.jpg` 里是 JPEG 魔数、`out2.png` 里是 PNG 魔数；
格式不符的 export 返回 `Err 目标扩展名与所选格式不符`，且**不留下半成品文件**。

### 8.3.4 顺带查清的一件事：resize 的尺寸语义

补断言时我按「塞进框内」写了期望值（2x3 → 框 4x4 ⇒ 4x4），**测试红了**。
读 image crate 源码（`resize_dimensions(w, h, nw, nh, fill=false)`）确认：
`ratio = min(nw/w, nh/h)`，**取 min**、不裁切 ⇒ 实测 3x4。

**断言写错就改断言，不改实现** —— 但这次改断言前先去读了源码，
确认是**我错了、不是实现错了**。记在这里是因为「按公式手推」和「读实现」差着一个 `fill` 分支。

### 8.6.1 CI 补了一道此前**根本不存在**的门

`.github/workflows/ci.yml` 三条流水线（macOS / Ubuntu / Windows）此前只跑
`cargo test` + `cargo clippy`，**没有 fmt 门**。后果是 cap-img 的

格式差异与平台无关 ⇒ 本地就能量 ⇒ 可以安全地加成硬门。
